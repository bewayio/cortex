# Module: release

## Purpose

Build BCode's desktop binaries for macOS, Linux and Windows via GitHub Actions, and publish them to a public release repository so they're ready for distribution (starting with a future Homebrew cask, later other package managers).

## Boundaries

- Owns: `.github/workflows/release.yml` (and any small helper scripts it needs), the versioned GitHub Releases on the public `bewayio/homebrew-bcode` repo, and (once set up) that repo's `Casks/bcode.rb` Homebrew cask formula.
- Does NOT own: application runtime behavior (every other module above), the actual Homebrew cask formula or any other package-manager packaging (future work, not part of this module yet), code signing/notarization (not attempted — binaries ship unsigned for now).

## Public Interface

None — this is a CI/CD pipeline (GitHub Actions), not a runtime API. It has no Wails-bound Go methods and no frontend components.

## Events Published

None (in the Wails-event sense). Externally, a successful run updates the `bewayio/bcode` GitHub Release — not something the running app itself observes or reacts to.

## Events Consumed

None.

## Dependencies

| Dependency | Type | Interface |
|-----------|------|-----------|
| GitHub Actions | external service | workflow YAML in `.github/workflows/` |
| Wails CLI | build tool | `wails build`, version pinned to match `go.mod`'s `github.com/wailsapp/wails/v2` |
| linuxdeploy (+ AppImage runtime) | build tool, Linux job only | bundles the Linux binary and its shared-library closure (incl. `libwebkit2gtk-4.0`) into one AppImage |
| Cross-repo publish credential | external, user-provisioned secret | a fine-grained PAT (or equivalent) with write access to `bewayio/bcode` only, stored as a GitHub Actions secret in `bewayio/code` |

## Areas

| Area | Permission Level |
|------|-----------------|
| CI/CD (GitHub Actions) | maintainer-only — triggered by pushes to the private `bewayio/code` repo, publishes to the public `bewayio/bcode` repo |

## Security

- The cross-repo publish credential must be scoped as narrowly as possible (write access to `bewayio/homebrew-bcode` only, not org-wide) and stored only as a GitHub Actions secret — never committed, never handled by an assistant on the user's behalf.
- No application secrets (DB passwords, the local encryption key from ADR-0009, chat history, etc.) are involved in or exposed by this pipeline — it only ever touches build inputs (source code) and build outputs (binaries).
- `bewayio/code` (source) stays private; `bewayio/homebrew-bcode` (binaries + cask) stays public and should never receive source code, only release assets and the cask formula itself.

## Notes

- **Planned 2026-09-27, user request.** Two-repo split, both already existing as empty/unrelated-content GitHub repos at the time of this spec: `bewayio/code` (private) becomes this project's actual source repo — **this working directory has no `.git` at all yet**; the public releases repo was described as intentionally "clean," ready for a Homebrew cask and, later, other Linux/Windows package managers (the latter still future work; the cask itself is now in scope, see below).
- **Repo renamed to `homebrew-bcode`, same day, user follow-up.** Homebrew's tap-shorthand convention (`brew tap bewayio/bcode`) requires the underlying GitHub repo to be named `homebrew-<tap-name>` — a plain `bcode` repo would only work via the full-URL tap syntax. The user is renaming `bewayio/bcode` → `bewayio/homebrew-bcode` on GitHub; every reference in this module and its task/workflow uses the new name.
- **Distribution mechanism**: GitHub Releases, not binaries committed into the repo's git tree — chosen on the user's confirmation, since committed binaries would make that repo's `.git` grow forever even as old versions are removed from view, and Releases is what a Homebrew cask (and most other package managers) expect anyway.
- **Trigger revised twice, same day, user follow-ups.** First revision: tag pushes (`v*`) instead of every push to `main` — the original rolling-"latest" design was incompatible with a cask's `sha256` pinning one exact checksum per version. Second revision (final): **back to every push to `main`**, but without any manual tagging — the user wanted pushing `bewayio/code` alone to be enough, with GitHub Actions inventing the version and creating the tag/release on `bewayio/homebrew-bcode` itself, not requiring the user to tag anything. The workflow computes `v${BASE_VERSION}.${{ github.run_number }}` (a workflow-level `BASE_VERSION` env var for manual major/minor bumps, `github.run_number` as an always-increasing patch number — unique per run, never reused), creates one real, permanent, versioned GitHub Release under that computed tag, and bundles a `checksums.txt` (sha256 per platform asset) into it — the cask pins these exact values per version, satisfying the same correctness requirement the first revision was for, without the manual tagging step.
- **Build strategy**: a 3-way OS matrix (`ubuntu-latest`, `macos-latest`, `windows-latest`), each building natively via `wails build` for its own platform — Wails apps are not cross-compiled (cgo + native webview bindings per OS), so there is no way to build all three from a single runner.
- **Known limitation, accepted for now**: binaries are unsigned/unnotarized. macOS will show a Gatekeeper warning on first launch; Windows SmartScreen may warn too. Code signing needs paid developer accounts/certificates on both platforms and is out of scope unless requested separately.
- **Homebrew cask, same day, user follow-up — now in scope**: `bewayio/homebrew-bcode` gets a `Casks/bcode.rb` file following Homebrew's cask DSL (`cask "bcode" do ... end`, `app "bcode.app"` for the macOS `.app` bundle from the release asset). Only the macOS asset is installable via a cask (Homebrew Cask is macOS-only by design) — Linux/Windows package managers remain future work, unaffected by this. Local working copy: `~/projetos/wails/bcode` (freshly cloned from the renamed, emptied repo — distinct from `~/projetos/bcode`, an older clone of the same repo under its *old* name/content, left untouched). `homepage` in the cask points at `bewayio/homebrew-bcode` itself, not `bewayio/code`, since the source repo is private and would 404 for `brew home`. The macOS bundle identifier is `com.wails.bcode` (Wails' default `com.wails.{{.Name}}` template, never customized in `build/darwin/Info.dev.plist`) — used for the cask's `zap` stanza. `version`/`sha256` in the cask are placeholders until the first real release exists; committed locally, not pushed. **Added same day, user follow-up**: a `postflight` block runs `xattr -rd com.apple.quarantine` on the installed `.app` — without it, macOS Gatekeeper blocks the unsigned binary on first launch. This trades away that OS protection specifically for this app; drop it once the app is actually code-signed/notarized. Homebrew's own audit/style checks don't apply here at all — those only run for PRs into the official `homebrew-core`/`homebrew-cask` repos, not for installs from a third-party tap like this one.
- **Bug found from a real CI run, 2026-09-29 (Linux)**: the Linux job failed compiling with `Package webkit2gtk-4.0 was not found` — exactly the risk flagged in the original workflow comment. Root cause confirmed: it's not just an apt package rename, Wails v2.12.0's own webview bindings look up `webkit2gtk-4.0` via pkg-config specifically (hardcoded), and `ubuntu-latest` had moved to Ubuntu 24.04, which dropped that package in favor of `webkit2gtk-4.1` — installing `libwebkit2gtk-4.1-dev` (the original guess) doesn't satisfy a pkg-config lookup for the `-4.0` name. Fixed by pinning the Linux matrix entry to `ubuntu-22.04` (still ships `libwebkit2gtk-4.0-dev`) instead of `ubuntu-latest`, reverting the apt package back to `-4.0-dev`. The `publish` job still uses `ubuntu-latest` — it never compiles anything webview-related, so it's unaffected.
- **Bug found from a real CI run, 2026-09-29 (macOS)**: the macOS build failed on `npm install` with a `403` fetching `zustand` from `npm.artifacts.furycloud.io`. Root cause found on user follow-up: `frontend/package-lock.json` had 254 `resolved` URLs hardcoded to that private registry — it must have been generated on a machine configured to use it, and `npm ci`/`npm install` use a lockfile's literal `resolved` URL per package regardless of the configured registry. Fixed by regenerating the lockfile from scratch on this machine (confirmed to use the real `registry.npmjs.org`, no `.npmrc` anywhere pointing elsewhere) — `npm run build` and `go build ./...` both verified clean against the new lockfile. Also added, as a defensive belt-and-suspenders measure (not the actual fix, but cheap insurance against the same class of problem recurring if the lockfile is ever regenerated on a differently-configured machine): `NPM_CONFIG_REGISTRY: https://registry.npmjs.org/` in the workflow's top-level `env:`. Also bumped `setup-node`'s `node-version` from `20` to `22` while investigating, since the same log showed an `EBADENGINE` warning for `chevrotain` (a transitive dependency) wanting Node ≥22. **Not yet re-verified with a real CI run** — the local build passes, but this hasn't been pushed and run on GitHub Actions yet.
- **"Always latest" download URLs for a future install script, 2026-09-30, user request**: the user wants a `.sh` installer (installs on any OS, similar in spirit to what Homebrew does for the cask on macOS) pointed at a stable, always-current download link. No workflow change was needed: GitHub's own `/releases/latest/download/<asset>` URL already redirects to whatever the most recent non-prerelease release is, and `ncipollo/release-action` marks each new release as latest by default (`makeLatest: true`) — since this pipeline's asset filenames never change between releases (no version in the filename), this built-in alias already behaves exactly like a maintained rolling "latest" release, with no extra publish step. The stable URLs: `https://github.com/bewayio/homebrew-bcode/releases/latest/download/bcode-linux-x86_64.AppImage` (updated 2026-10-01 — was `bcode-linux-amd64.tar.gz`, see AppImage packaging entry below), `.../bcode-macos-universal.zip`, `.../bcode-windows-amd64.zip`, `.../checksums.txt`. The install script (not yet written) should verify the downloaded asset's sha256 against `checksums.txt` before running it.
- **Linux runtime failure, 2026-09-30, user report**: the plain Linux binary (`bcode-linux-amd64.tar.gz`) fails on launch with `error while loading shared libraries: libwebkit2gtk-4.0.so.37: cannot open shared object file: No such file or directory` on systems that don't have `libwebkit2gtk-4.0` installed — the same package family already flagged as a moving target during the CI build fix (Ubuntu 24.04 dropped `-4.0` for `-4.1`), now confirmed to bite end users too, not just CI runners. **Decision (user-confirmed): package Linux as an AppImage instead of a plain tarball.** An AppImage bundles the binary together with its shared-library closure (via `linuxdeploy`, run in the Linux matrix job after `wails build`) — including `libwebkit2gtk-4.0` itself — into one self-contained, executable file that runs on any glibc-based distro without the user installing anything system-wide. This replaces `bcode-linux-amd64.tar.gz` as the Linux release asset (tracked as `bcode-linux-x86_64.AppImage`, the AppImage project's own naming convention); `checksums.txt` and the future install script's Linux download URL both need updating to match. Scoped to this module only — no ADR, consistent with how this module's other packaging decisions (cask, trigger revisions) have been recorded as Notes rather than ADRs.
- **Bug found from a real run, 2026-10-01 (Linux AppImage)**: launching the AppImage failed with `Unable to spawn a new child process: ... WebKitNetworkProcess (Arquivo ou diretório inexistente)`, pointing at the exact system path (`/usr/lib/x86_64-linux-gnu/webkit2gtk-4.0/WebKitNetworkProcess`) this AppImage exists to avoid depending on. First attempted fix (2026-10-01): copy the libexec directory into the AppDir by hand and set a `WEBKIT_EXEC_PATH` env var via `linuxdeploy`'s `apprun-hooks` — **this did not work** (confirmed by a second real run, 2026-10-02, identical crash). **Root cause, found 2026-10-02 after reading Wails' own upstream issue/fix for this exact problem** ([issue #4313](https://github.com/wailsapp/wails/issues/4313), [PR #6213](https://github.com/wailsapp/wails/pull/6213)): WebKitGTK does not read any env var for this — the helper-process directory is an absolute path **compiled into `libwebkit2gtk` itself** as a fixed C string, hardcoded to wherever it was built (Debian/Ubuntu's `/usr/lib/x86_64-linux-gnu/webkit2gtk-4.0`). The real fix, matching Wails' own: binary-patch that compiled-in path inside the deployed `.so` files, replacing the leading `/usr` with `././` — same byte length (safe in-place patch, no offsets shift) — so the path becomes relative; `linuxdeploy`'s own generated `AppRun` `cd`s into `$APPDIR/usr` before exec'ing the real binary, so the relocated relative path resolves straight to the helper binaries already bundled there. Implemented as a two-stage `linuxdeploy` run (deploy-only pass → Python same-length byte patch on `libwebkit2gtk*`/`libjavascriptcoregtk*` → pack-only pass), replacing the broken `WEBKIT_EXEC_PATH`/`apprun-hooks` attempt entirely.
- **Bug found from a real run, 2026-10-03 (first instance)**: the patch script's hand-typed replacement string (`"././lib/..."`) was one byte shorter than the original (missing a `/`), so `assert len(old) == len(new)` failed immediately (before even reaching a file). Fixed by deriving the replacement programmatically — `new = b"././" + old[len(b"/usr"):]` — instead of hand-counting characters in a second literal string.
- **Bug found from a real run, 2026-10-03 (second instance, same crash persisted)**: the length-assert fix above made the script *run* correctly, but it still patched nothing — because the glob only looked under `AppDir/usr/lib/x86_64-linux-gnu/`, assuming `linuxdeploy` preserves that Debian arch-triplet subdirectory. `linuxdeploy` commonly flattens bundled shared libraries directly into `AppDir/usr/lib/` instead, so the glob silently matched zero files — no error, no print, just a no-op, and the unpatched library (wherever it actually landed) still had the old absolute path. Fixed by walking the entire `AppDir` tree and patching whichever file(s) actually contain the byte string, instead of assuming a specific layout; also added `assert patched > 0` so a future layout change (or any other reason nothing matches) fails the build loudly instead of silently shipping a still-broken AppImage a third time.
- **Root cause fully understood and verified end-to-end, 2026-10-03, after the user reported the crash still happened on a machine where `wails dev` worked fine** — which turned out to be fully consistent, not contradictory: that machine is Ubuntu 24.04 (only ships `webkit2gtk-4.1`; a `webkit2gtk-4.0.pc` pkg-config compat shim exists, satisfying `wails dev`'s build-time linking, but no real `/usr/lib/x86_64-linux-gnu/webkit2gtk-4.0/` directory exists at runtime) — i.e. a second real machine confirming the same cross-distro bug the AppImage exists to fix. Reproduced the full pipeline in disposable Docker containers (one matching the CI build environment, Ubuntu 22.04; one clean Ubuntu 24.04 with zero webkit2gtk packages, matching the user's report) to verify for real instead of guessing a fourth time. This surfaced **two more bugs** beyond the glob issue above, both now fixed:
  1. `linuxdeploy`'s own generated `AppRun` does **not** `cd` anywhere before exec'ing the real binary (despite the upstream Wails PR's description implying it does) — the relative path from the binary patch was resolving against whatever directory the AppImage happened to be launched from, not `$APPDIR/usr`. Fixed by `sed`-patching `AppDir/AppRun` to `cd "$this_dir/usr"` right before the final `exec`.
  2. Packaging via `linuxdeploy --appdir AppDir --output appimage` **silently regenerates `AppDir/AppRun` from scratch**, wiping the `cd` patch from (1) before the final package was ever produced. Fixed by downloading `appimagetool` directly and invoking it on `AppDir` instead of going through `linuxdeploy`'s own output step a second time.
  3. Once the helper process was actually found and spawned, it failed with its own `error while loading shared libraries: libwebkit2gtk-4.0.so.37` — `linuxdeploy` sets each helper binary's rpath to `$ORIGIN` (its own directory), but the bundled `libwebkit2gtk-4.0.so.37` these helpers depend on lives one level up (`linuxdeploy` flattens shared libraries into `usr/lib/`, not the nested libexec directory). Fixed by also exporting `LD_LIBRARY_PATH="$APPDIR/usr/lib"` in the same `AppRun` patch.
  **Verified working**: the resulting AppImage ran for 10+ seconds without crashing in a clean Ubuntu 24.04 container with zero webkit2gtk packages installed (Xvfb + software GL, no real display needed) — the exact failure mode reported. Not yet re-verified with a real CI run (the Docker reproduction used the same build steps but is not the GitHub Actions runner itself), but this is now a *verified fix*, not another guess.
- **Corrigido 2026-10-17, pedido do usuário — build local falhou com `FATAL ERROR: Ineffective mark-compacts near heap limit... Adicionado ao `release.yml`'s step `Build` como `env:` — seguro mesmo em runners com bastante RAM livre, sem custo real. **Não verificado ainda em uma run real do GitHub Actions.**

Corrigido: `bin`/`asset` da matrix de build viraram `cortex`/`cortex.app`/`cortex.exe` e `cortex-{linux-x86_64.AppImage,macos-universal.zip,windows-amd64.zip}`; os `cp`/`--desktop-file`/`--icon-file` do passo de empacotamento Linux apontam pro `cortex.desktop`/`cortex.png`; o `grep` do passo de atualização do cask Homebrew procura por `cortex-macos-universal.zip` (nome do asset) em vez de `bcode-macos-universal.zip`.

O `sed` deste workflow só atualiza `version`/`sha256` do cask, não o `url` — o cask vai apontar pro nome de asset errado até alguém editar `url` nesse arquivo, no repositório externo, à mão.
- **Corrigido 2026-10-14, pedido do usuário — ícone genérico (engrenagem) depois de instalar via o instalador `cortex.sh` de outro projeto (`freeskills`).** Causa raiz **fora deste repositório**: `cortex.sh` baixa o AppImage puro e escreve um `.desktop` com `Icon=application-x-executable` fixo — nunca instalava um ícone de verdade, já que não existia nenhum asset de ícone pra baixar. Corrigido nos dois lados:
  1. **Aqui** (`release.yml`): novo passo `Prepare icon asset (Linux leg only)` copia `build/appicon.png` pra `cortex-icon.png` (só na perna Linux do build matrix, já que o ícone independe de plataforma), com checksum próprio (`cortex-icon.png.sha256`) publicado junto no mesmo `checksums.txt` de sempre — um novo artefato de release, `cortex-icon.png`, baixável em `.../releases/latest/download/cortex-icon.png` igual aos outros assets.
  2. **No `freeskills/cortex.sh`** (projeto irmão, fora deste repo — `~/projetos/freeskills/freeskills/cortex.sh`): o trecho Linux agora baixa `cortex-icon.png`, confere o checksum (não-fatal — falha aqui não aborta a instalação do app em si), instala em `~/.local/share/icons/hicolor/512x512/apps/cortex.png` (tema de ícones padrão do usuário, resolvido por `Icon=cortex` no `.desktop`), roda `gtk-update-icon-cache`/`update-desktop-database` se existirem (ignorando erro se não existirem), e só cai de volta pro `Icon=application-x-executable` genérico se o download/checksum do ícone falhar (ex: release antiga, de antes desta correção, sem esse asset ainda). Testado com um dry-run local (release falsa num diretório temporário, `$HOME` isolado) cobrindo os dois casos — ícone disponível e ícone ausente.
